`EntityHeader` is the detail-page header. You supply content — a title, some stats, some facts — and it owns the layout, the density, the responsive reflow, and the loading skeletons.

It deliberately does **not** render breadcrumbs, the page `h1`, or global actions. Those belong to the TopBar and its slots (`TopBar.Slot name="breadcrumbs"` / `"title"`), which already own them. The title here is an `h2`.

## Only the title is required

Every other slot is optional, and the grid template is built from whichever you pass — so an omitted slot leaves no empty row behind.

</Storybook.Demo>


## Leading graphic

`title.leadingGraphic` is data, not a node, so the header controls the size — 24px, matching the avatars in the people slot — and the slot cannot be used to smuggle in a component.

```jsx
leadingGraphic={{type: 'user', user: replay.user}}
leadingGraphic={{type: 'project', projects}}
leadingGraphic={{type: 'platform', platform: 'javascript'}}
```

`project` and `platform` draw the same badge but take what the caller actually holds. A trace knows its projects and the header maps them to platforms; a build has only inferred a platform from a file type. A `project` graphic with no known platform renders nothing rather than falling back to an all-projects glyph, which belongs to a saved view.

The graphic is decorative by default: a platform icon next to "ValueError" tells a screen reader nothing the title has not. Give it a `label` when it carries something the title does not — which projects a trace touched, say — and it becomes an image in its own right, reachable by keyboard, with `tooltip` for richer hover content than the label.

```jsx
leadingGraphic={{
  type: 'project',
  projects,
  label: t('%s projects', projects.length),
  tooltip: <ProjectListTooltip projects={projects} />,
}}
```

## People

People related to the entity get their own slot rather than being a labelled stat: they have no value to show, and they usually load on a different schedule from the entity itself. Pass the users and let the header render the stack.

`label` is required, because a stack of faces says nothing on its own — it heads each avatar's tooltip. `collectiveNoun` names the overflow chip, which otherwise reads "+3 other people".

```jsx
// Replay — who watched it
<EntityHeader
  title={{label: replay.user.display_name}}
  people={{users, label: t('Viewed by'), collectiveNoun: t('viewers'), isLoading}}
  stats={[{label: 'Errors', value: 2}]}
/>

// Issue — who is involved in it
<EntityHeader
  title={{label: 'ValueError'}}
  people={{users: participants, label: t('Participants')}}
/>
```

The slot keeps its space while `isLoading`, which is what stops the stats sliding sideways when the avatars land. Once it resolves to nobody it renders nothing, and the divider before the first stat goes with it.

## Conditional items

`stats`, `metadata` and `tags` drop `null` entries, so you can inline a conditional instead of building the array ahead of time. Items are keyed by their position in the array you wrote, not in the filtered result, so an item appearing or disappearing never remounts its neighbours.

```jsx
<EntityHeader
  title={{label: replay.user.display_name}}
  stats={[
    isVideoReplay
      ? null
      : {type: 'text', label: 'Dead Clicks', value: replay.count_dead_clicks},
    {type: 'text', label: 'Errors', value: errors.length},
  ]}
/>
```

## Stat types

A stat declares whether it is `text` or a `link`. That is not just documentation: a stat whose type depended on its data would render a different element once the data arrived, and swapping a span for an anchor mid-load moves the row. So a stat that links, links from the first render — including when its count is still zero.

```jsx
{type: 'text', label: t('Rage Clicks'), value: 2}
{type: 'link', label: t('Errors'), value: errors.length, to: errorsTab}
```

The value may change as often as it likes. The type may not.

## Stat tooltips

A stat holds one number. Anything that explains it — what the label means, what the value is made of — belongs in a tooltip, not in the row.

`labelTooltip` covers a label that is jargon on its own. `valueTooltip` carries a breakdown: a replay's errors can come from several projects, so the stat shows the total and the tooltip splits it by project. Both take structured content, so they can be built from `Tooltip.Header`, `Tooltip.Grid` and `Tooltip.Row`.

```jsx
stats={[
  {
    type: 'text',
    label: t('Dead Clicks'),
    value: 4,
    labelTooltip: t('A click that did not change anything on the page.'),
  },
  {
    type: 'link',
    label: t('Errors'),
    value: errors.length,
    to: errorsTab,
    valueTooltip: (
      <Fragment>
        <Tooltip.Header>{t('Errors')}</Tooltip.Header>
        <Tooltip.Grid columns="max-content 1fr max-content">
          {byProject.map(([slug, count]) => (
            <Tooltip.Row key={slug} leadingItems={<ProjectAvatar …/>} trailingItems={count}>
              {slug}
            </Tooltip.Row>
          ))}
        </Tooltip.Grid>
      </Fragment>
    ),
  },
]}
```

A value with a `valueTooltip` and no `to` renders as `InfoText`, so it gains the dotted underline and is reachable by keyboard. A value that also links gets the same underline, but from the tooltip directly rather than through `InfoText`, which would put a second tab stop inside the anchor. The link alone is not enough of a signal: the global anchor colour is overridden by the `Text` inside it, which keeps the stat's own `content.primary`.

## Loading

Pass `isLoading` and each slot renders a skeleton sized from the typography it will hold. Because the skeleton comes from the same declarations as the loaded state, the two cannot drift apart — there is no placeholder twin to keep in sync.

Each slot is replaced whole, stat labels included. A label is static and could be shown straight away, but a half-drawn stat next to a loading title reads as broken. Size `loadingWidth` to the content you expect so the row does not jump when the value lands.

## Responsive behaviour

The header reflows against **its container's** width, not the viewport's — on a routed page that is the content column, so it reacts correctly when a side panel opens.

Above the `lg` container breakpoint (640px) the stats sit to the right of the title. Below it they move to their own row _beneath_ the metadata and left-align. That is a reorder rather than a wrap, which is why the layout is a grid.

640px is where a title and a typical stat row first fit side by side, which is wider than the nominal 500px band in the spec — below it the title gets squeezed by a stat row whose width the header cannot know in advance.

## When to use

Use `EntityHeader` on a detail page — a single issue, trace, replay, release, or build. It is the shared replacement for hand-rolled header blocks built from `Layout.Header` or bespoke styled grids.

Do not use it for list or landing pages, which carry no single entity.

## Accessibility

- The title renders as an `h2`. The page's `h1` is the TopBar title slot, so the two do not compete.
- A `leadingGraphic` is decorative and hidden from assistive technology; the title label carries the meaning.
- A metadata `tooltip` is keyboard accessible, with a dotted underline signalling it is there.
