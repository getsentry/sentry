import {Tag} from '@sentry/scraps/badge';
import {EntityHeader} from '@sentry/scraps/entityHeader';

import {IconCalendar} from 'sentry/icons';
import * as Storybook from 'sentry/stories';

export const documentation =
  import('!!type-loader!@sentry/scraps/entityHeader/entityHeader');

`EntityHeader` is the detail-page header. You supply content — a title, some stats, some facts — and it owns the layout, the density, the responsive reflow, and the loading skeletons.

It deliberately does **not** render breadcrumbs, the page `h1`, or global actions. Those belong to the TopBar and its slots (`TopBar.Slot name="breadcrumbs"` / `"title"`). The title here is an `h2`.

It reflows against **its container's** width, not the viewport's — on a routed page that is the content column, so it reacts when a side panel opens. Above the `lg` container breakpoint (640px) the stats sit beside the title; below it they move to their own row _beneath_ the metadata and left-align. That is a reorder rather than a wrap, which is why the layout is a grid. Every example on this page sits in a resizable window, so you can drag any of them past the breakpoint to watch it.

## Usage

Use `EntityHeader` on a detail page — a single issue, trace, replay, release, or build. Not on list or landing pages, which have no one entity to be about.

<Storybook.Demo resizable direction="column" align="stretch">
  <EntityHeader
    title={{
      label: 'Replay user',
      value: 'anonymous@example.com',
      tags: [
        <Tag key="live" variant="success">
          Live
        </Tag>,
      ],
    }}
    stats={{
      label: 'Replay stats',
      items: [
        {type: 'text', label: 'Dead Clicks', value: 0},
        {type: 'text', label: 'Rage Clicks', value: 2},
        {type: 'link', label: 'Errors', value: 1, to: '/replays/1/?t_main=errors'},
      ],
    }}
    metadata={{
      label: 'Replay properties',
      items: [
        {
          label: 'Started at',
          values: ['Feb 11, 2026 10:56 CET'],
          leadingGraphic: <IconCalendar size="md" />,
        },
        {label: 'Browser', values: ['Chrome', '144.0.0']},
        {label: 'Operating system', values: ['Windows', '>=10']},
      ],
    }}
  />
</Storybook.Demo>

```jsx
<EntityHeader
  title={{label: t('Replay user'), value: replay.user.display_name}}
  people={{users: viewers, label: t('Viewed by')}}
  stats={{
    label: 'Replay stats',
    items: [{type: 'link', label: t('Errors'), value: errors.length, to: errorsTab}],
  }}
  subtitle={{content: replay.summary}}
  metadata={{
    label: t('Replay properties'),
    items: [{label: t('Browser'), values: ['Chrome', '144.0.0']}],
  }}
/>
```

Only `title` is required. The grid template is built from whichever other slots you pass, so an omitted one leaves no empty row behind.

`stats`, `metadata.items` and `title.tags` drop `null` entries, so a conditional can be written inline. Items are keyed by their position in the array you wrote rather than in the filtered result, so one appearing or disappearing never remounts its neighbours.

```jsx
stats={{label: 'Replay stats', items: [
  isVideoReplay ? null : {type: 'text', label: t('Dead Clicks'), value: deadClicks},
  {type: 'text', label: t('Errors'), value: errors.length},
]}}
```

### Loading

Pass `isLoading` and every slot renders a skeleton sized from the typography it will hold. The skeleton comes from the same declarations as the loaded state, so the two cannot drift apart — there is no placeholder twin to maintain.

Each slot is replaced whole, stat labels included. A label is static and could be shown straight away, but a half-drawn stat next to a loading title reads as broken rather than as loading. Size `loadingWidth` to the content you expect, so the row does not jump when the value lands.

<Storybook.Demo resizable direction="column" align="stretch">
  <EntityHeader
    isLoading
    title={{label: 'Replay user', value: 'anonymous@example.com'}}
    stats={{
      label: 'Replay stats',
      items: [
        {type: 'text', label: 'Dead Clicks', value: 0},
        {type: 'text', label: 'Errors', value: 1},
      ],
    }}
    metadata={{
      label: 'Replay properties',
      items: [
        {label: 'Started at', values: ['Feb 11, 2026 10:56 CET']},
        {label: 'Browser', values: ['Chrome', '144.0.0']},
      ],
    }}
  />
</Storybook.Demo>

```jsx
<EntityHeader
  isLoading={!replayRecord}
  title={{label: t('Replay user'), value: displayName, loadingWidth: '200px'}}
  stats={{
    label: 'Replay stats',
    items: [
      {type: 'text', label: t('Errors'), value: errors.length, loadingWidth: '64px'},
    ],
  }}
/>
```

A declared slot holds its space before its contents arrive. Passing `metadata` reserves the row even while every item is still `null`, and passing `subtitle` reserves its line even while `content` is empty — so a header whose data all lands at once does not grow a row and push the page down. Only an omitted slot leaves no row behind.

Slots that resolve on their own schedule carry their own flag, additive to the header's: `people.isLoading` for the avatar stack, and `isLoading` on an individual stat. Use the latter when a count arrives after the entity does — an issue knows its title before it knows how many events it has, and a stat without the flag would render the zero it happens to hold. The entity's own fields stay live throughout.

```jsx
stats={{label: 'Replay stats', items: [
  {type: 'text', label: t('Events'), value: count, isLoading: isCountPending},
]}}
```

The header sets `aria-busy` while any slot is loading. Note that this is a state in the accessibility tree, not an announcement — no screen reader reads it. A page that needs the transition announced has to add its own live region.

## Title

A title is a `label` and a `value`. The `value` renders — it is the entity's name. The `label` says what that name _is_, and is not rendered.

```jsx
title={{label: t('Replay user'), value: replay.user.display_name}}
```

### Accessibility

The title is an `h2`, named from both halves, so heading navigation lands on "Replay user, anonymous@example.com" rather than a bare string.

That is why `label` is required. A sighted reader knows `anonymous@example.com` is a person from the avatar beside it and the breadcrumb above it; someone jumping straight to the heading has neither. The label is the text equivalent of what the avatar is doing visually — which is also why it is the one label in this component that is not rendered.

The title is never a link. A heading that is wholly a link announces as both, and the breadcrumb above it already handles going up. While loading, the heading stays in the tree named by its `label` alone, so the page's structure does not change as data lands and no value is asserted before it is known.

### Leading graphic

`title.leadingGraphic` is data, not a node, so the header controls the size and the slot cannot be used to smuggle in a component.

<Storybook.Demo resizable direction="column" align="stretch" gap="xl">
  <EntityHeader
    title={{
      label: 'Replay user',
      value: 'alice@example.com',
      leadingGraphic: {
        type: 'user',
        user: {id: '1', name: 'Alice Chen', email: 'alice@example.com'},
      },
    }}
  />
  <EntityHeader
    title={{
      label: 'Trace',
      value: 'GET /api/0/organizations/',
      leadingGraphic: {
        type: 'project',
        projects: [
          {slug: 'frontend', platform: 'javascript'},
          {slug: 'backend', platform: 'python'},
          {slug: 'checkout', platform: 'php'},
        ],
        label: '3 projects',
        tooltip: 'frontend, backend, checkout',
      },
    }}
  />
  <EntityHeader
    title={{
      label: 'Release',
      value: 'javascript-sdk @ 8.42.0',
      leadingGraphic: {type: 'platform', platform: 'javascript'},
    }}
  />
</Storybook.Demo>

```jsx
// Decorative. The title beside it already says who this is.
leadingGraphic={{type: 'user', user: replay.user}}

// Named, and elaborating on hover. `tooltip` is only reachable once there is
// a `label` for it to attach to — the pair is unrepresentable otherwise.
leadingGraphic={{
  type: 'project',
  projects,
  label: t('%s projects', projects.length),
  tooltip: <ProjectListTooltip projects={projects} />,
}}

// Same badge, for a caller that has a platform but no project.
leadingGraphic={{type: 'platform', platform: 'javascript'}}
```

`project` and `platform` draw the same badge but take what the caller actually holds: a trace knows its projects and the header maps them to platforms, a build has only inferred a platform from a file type. A `project` graphic whose projects have no known platform falls back to the generic platform tile, not to the all-projects glyph — that one means a saved view, not an entity.

The box is always 24px. A project or platform badge fills it; a user avatar is drawn at 20 and centred, because the avatars in the people slot are 24 with a 2px border and so show a 20px disc — a borderless 24 here would be the larger of the two circles in the same header.

The graphic is decorative by default — a platform icon next to "ValueError" tells a screen reader nothing the title has not. Give it a `label` when it carries something the title does not, such as which projects a trace touched, and it becomes an image in its own right.

It is deliberately not focusable, since a named image is announced without focus. That makes `tooltip` mouse-only: use it for elaboration and keep anything a user needs in `label`.

### Tags

`title.tags` takes `Tag` elements, rendered inline after the value. Use them for status that belongs to the entity itself — live, archived, pre-release.

```jsx
tags={[isLive ? <Tag key="live" variant="success">{t('Live')}</Tag> : null]}
```

They are siblings of the heading, not part of it, so a tag's text is not in the heading's accessible name. Someone navigating by heading hears the title and not the tag. Keep tags to state that is reinforced elsewhere on the page, and do not let one be the only place something is said.

## Stats

A stat is one measurement: a `label` naming it and a `value`. Both are rendered, on a shared baseline.

```jsx
stats={{label: 'Replay stats', items: [{type: 'text', label: t('Rage Clicks'), value: 2}]}}
```

Keep the value to the single number the label names. Anything that explains it belongs in a tooltip, not in the row — a stat that renders its own detail inline fights the density the row is built for.

### Accessibility

The row is a list, and `label` names it — "Replay stats". Without it a screen reader meets a run of numbers with nothing saying what they count. People sit beside that list rather than inside it: a list named for its stats cannot hold something that is not one.

A stat is one fact split across two elements, which a screen reader moving element by element otherwise reads as two: "0", then "Dead Clicks".

On a `link` stat the anchor is named from the value and the label together, so it reads "4 Dead Clicks" in one go, and the value is hidden since the name already speaks it. A `text` stat is still two elements — adjacent and read in order, but visited separately.

That is why a `link` stat's `value` is text rather than a node: the name is composed from it. A graphic there would leave the link named by its label alone, silently dropping the half that says how many.

### Types

A stat declares whether it is `text` or a `link`. That is not only documentation. A stat whose type depended on its data would render a different element once that data arrived, and swapping a span for an anchor mid-load moves the row. So a stat that links, links from the first render — including when its count is still zero.

```jsx
{type: 'text', label: t('Rage Clicks'), value: 2}
{type: 'link', label: t('Errors'), value: errors.length, to: errorsTab}
```

The value may change as often as it likes. The type may not.

On a `link` stat it is the **label** that navigates, not the value: a link named by its own digits says nothing in a screen reader's links list.

### Tooltips

`labelTooltip` covers a label that is jargon on its own. `valueTooltip` carries a breakdown — a replay's errors can come from several projects, so the stat shows the total and the tooltip splits it by project. Both take structured content, so either can be built from `Tooltip.Header`, `Tooltip.Grid` and `Tooltip.Row`.

`valueTooltip` is only available on a `text` stat. On a link the value is hidden, and a tooltip needs a visible, focusable trigger — put the breakdown in `labelTooltip`, where it attaches to the link.

Colour says it navigates; an underline says it explains. A link label is accent-coloured, a tooltipped label is underlined, and one that does both is both — as the three stats below are, in order. A single treatment would mean a link that only navigates looked like one that explains, and an underline reads as "hover for more" to most people, so that is the meaning it keeps.

## People

People related to the entity get their own slot rather than being a labelled stat: they have no value to show, and they usually load on a different schedule from the entity itself.

```jsx
// Replay — who watched it
people={{users: viewers, label: t('Viewed by'), isLoading}}

// Issue — who is involved in it
people={{users: participants, label: t('Participants')}}
```

The slot keeps its space while `isLoading`, which is what stops the stats sliding sideways when the avatars land. Once it resolves to nobody it renders nothing, and the divider before the first stat goes with it.

### Accessibility

The people are read out by name — "Viewed by: Alice, Bob" — and the avatars themselves are decorative.

A stack of faces says nothing on its own, which is why `label` is required. The avatars cannot carry the names either: most people have no uploaded avatar, and a letter avatar reaches the accessibility tree as initials with an unreliable name. They are also not focusable, so their hover tooltips never reach a keyboard user, and nor does the overflow chip. Naming everyone as text answers all three, and does not depend on a screen reader announcing a `group` role.

## Metadata

The metadata row is a list of properties. Each item is one property: a `label` saying what it is, and one or more `values`.

```jsx
metadata={{
  label: t('Replay properties'),
  items: [
    {
      label: t('Browser'),
      values: [browser.name, browser.version],
      leadingGraphic: <PlatformIcon platform={platform} size="16px" />,
    },
  ],
}}
```

Two values rather than one joined string is the point: a browser is its name _and_ its version, and joining them at the call site loses that. An item needs at least one — a label followed by nothing reads as a property that failed to load.

`tooltip` adds an explanation on hover, with an underline to signal it.

### Accessibility

The row's `label` names it. Without one a screen reader meets a run of unrelated strings with nothing saying they belong together, or to what.

Each item's own label is in the DOM whether or not it is on screen, so an item is one stop that reads "Started at, 2 hours ago". `mode` decides whether that label is also drawn — `compact` leaves naming the property to the graphic beside it, `full` spells it out. Either way the label is announced; the mode is a question of visibility only.

A description list would tie each label to its value structurally, which sounds like the better answer and is not: marking them up as a `dt` and a `dd` made VoiceOver narrate the pairing itself — "term", then "selectable list item", then "end of term" — before it reached the value. One named item beats two correctly-related ones.

### Variants

`variant` colours the values. It defaults to `muted`; use a semantic variant to call out a problem, the way Issue Details renders "Unhandled" in `danger`.

```jsx
items={[
  {label: t('Mechanism'), values: ['generic'], mode: 'full', variant: 'primary'},
  {label: t('Level'), values: ['error'], mode: 'full', variant: 'muted'},
  {label: t('Handling'), values: [t('Unhandled')], mode: 'full', variant: 'danger'},
  {label: t('Status'), values: [t('Resolved')], mode: 'full', variant: 'success'},
  {label: t('Trend'), values: [t('Regressed')], mode: 'full', variant: 'warning'},
]}
```

The set is narrower than `ContentVariant` — `primary`, `muted`, `danger`, `success`, `warning` — because a tooltipped item also has to colour its underline, and `Tooltip` supports fewer. Keeping one list means the two cannot disagree.
